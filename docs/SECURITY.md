# Безопасность VaultCore: что защищено, что нет и где легко ошибиться

Документ для тех, кто будет читать код или переносить идею в другой стек.
Здесь собраны требования, запреты и — главное — типичные ошибки реализации,
которые выглядят безобидно, но обесценивают всю защиту.

---

## 1. Явные запреты ТЗ и как они выполнены

| Запрет | Как выполнено |
|---|---|
| Не хранить закрытый ключ в открытом виде | Windows: `CryptProtectData` (DPAPI), файл `key.blob` — только шифротекст; macOS/Linux: `keyring`; иначе — ключ только в памяти и пометка об этом |
| Не хранить ключ в коде/ресурсах | В сборку вшивается **только** открытый ключ (`embedded.py`); закрытый генерируется на устройстве |
| Не экспортировать закрытый ключ через UI | В интерфейсе нет такой функции; API хранилища наружу отдаёт только открытый ключ и подпись |
| Не писать свою криптографию | `cryptography` (Ed25519), `hashlib` (SHA-256); ни одного собственного примитива |
| Не использовать MD5/SHA-1 | Нигде не импортируются; тесты и код используют SHA-256 |
| Открытый ключ проверки вшит в сборку | `src/vaultcore/embedded.py`, генерируется `tools/embed_key.py` |
| Строгий разбор формата | `canonical.loads`: дубликаты ключей, лишние поля, неверные типы, не-UTC-даты, неканонический текст — отказ |
| Подписывается всё | Канонические байты = домен + `v` + заголовок + текст + `ts` (см. `docs/FORMAT.md`) |

## 2. Типичные ошибки реализации (и что здесь сделано иначе)

| Ошибка | Почему это ломает защиту | Как сделано здесь |
|---|---|---|
| Подписывать строку JSON «как есть» | другой порядок ключей / пробелы ломают проверку; трудно воспроизвести в другом языке | подписываются поля с префиксами длины; JSON — только транспорт |
| Подписывать только текст | заголовок и дату можно подменить | подписываются `v`, `title`, `text`, `ts` |
| Доверять дайджесту, приложенному к документу | проверяющий подтвердит подпись от подложенного хеша, а не от текста | дайджест в коде не передаётся, всегда пересчитывается |
| Игнорировать неизвестные поля | «безобидное» поле можно добавить и трактовать в другой версии верификатора | лишние поля = отказ, версия строго `1` |
| Сравнивать подписи/ключи `==` | утечка по времени (для ключей — теоретическая, но зачем) | `hmac.compare_digest` |
| ECDSA без канонизации `s` | из одной подписи получается вторая валидная (malleability) | выбран Ed25519: подписи детерминированы и неканоничных вариантов нет |
| Хранить ключ в файле рядом с программой | копируется вместе с папкой и работает на другом ПК | ключ только в хранилище ОС; DPAPI привязывает к учётке/машине |
| Тихо создавать новый ключ, если старый не расшифровался | получатели «теряют» автора, а приложение этого не замечает | явная ошибка с объяснением |
| Проверять подпись ключом из самого документа | документ подтверждает сам себя | ключ берётся из сборки (вшит), подменить в UI нельзя |
| Подписывать PDF-файл целиком | любая правка оформления/пересохранение ломает «подпись» | подписывается содержимое; PDF — представление |
| Показывать содержимое «изменённого» документа | подделка читается как настоящая, красная плашка теряется | при недействительной подписи содержимое не показывается |
| Терпимость к «похожим» кодам (лишние `=`, переносы внутри) | можно «починить» подпись и выдать искажённое за оригинал | переносы/пробелы допускаются только как обёртка при вставке; сам код строгий |
| Проверка даты по локальным часам получателя | «документ создан в будущем» выглядит нормально | дата берётся из подписанного `ts`, локальное время — только справочно |
| Незащищённый QR/ссылка | QR — это тот же код, его можно заменить | QR и ссылка дублируют код, проверка всегда по коду |

## 3. Что НЕ защищено (честно)

1. **Доступ к учётной записи.** Кто вошёл в систему под вашим пользователем,
   может подписывать документы от вашего имени: DPAPI защищает от копирования
   файлов, а не от живого доступа.
2. **Часы автора.** Без TSA дата — локальная. Автор может поставить системные
   часы назад и «запечатать» документ прошлым временем. Документ сам об этом
   предупреждает.
3. **Автор как противник.** Схема доказывает неизменность после подписи, но не
   добросовестность автора. Если нужно «автор недоверенный» — нужен аппаратный
   токен (Рутокен/YubiKey), ключ на котором нельзя скопировать.
4. **Утечка до подписи.** Пока документ не запечатан, текста нет нигде, кроме
   памяти процесса.
5. **Память процесса.** Python не даёт гарантий затирания: мы затираем
   `bytearray` с сидом сразу после подписи, но копии в куче/стеке ОС может
   остаться. Для полноценной защиты нужен код на языке с контролем памяти или
   аппаратный токен.
6. **Криптобиография ключа.** Приложение не публикует ключ сам — публикация
   (сайт, соцсети, визитка) остаётся за автором. Проверяющий должен получить
   отпечаток по независимому каналу, иначе доверять нечему.
7. **Скриншоты и PDF вне приложения.** Кто угодно может перерисовать документ
   и убрать штамп: защита — только при проверке кода в приложении.

## 4. Требования к эксплуатации

* Публикуйте **отпечаток** ключа (8 байт в hex) там, где получатель может
  проверить подлинность канала публикации.
* Не публикуйте `key.blob` — это не ключ, но и не сувенир: файл бессмысленно
  копировать, а вопросов он создаёт много.
* Храните `.poi`/PDF отдельно от приложения: приложение не является резервной
  копией (это прямо сказано в соглашении).
* Проверяйте, что в окне «Проверка» показан **тот** отпечаток ключа, который
  вы опубликовали: приложение показывает его в карточке ключа.

## 5. Проверка сборки на «чистоту» (для аудита)

```powershell
# 1. В сборке проверки не должно быть DPAPI-кода в действии:
#    вкладка «Создание» отсутствует (--mode verify).
# 2. Открытый ключ вшит, закрытого нет:
Select-String -Path src\vaultcore\embedded.py -Pattern "EMBEDDED_PUBLIC_KEY_B64"
# 3. В коде нет запрещённых примитивов:
Select-String -Path src\**\*.py -Pattern "md5|sha1\(" -CaseSensitive:$false
# 4. Тесты криптографии и формата:
python -m pytest tests -q
```
