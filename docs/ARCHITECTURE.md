# Архитектура VaultCore

## 1. Выбор стека

| Вариант | Плюсы | Минусы для этой задачи | Решение |
|---|---|---|---|
| **Python 3.11+ / PySide6** | один код на Windows/macOS/Linux; зрелые библиотеки криптографии и PDF; DPAPI доступен из `ctypes` без зависимостей; быстрая проверяемая разработка | нужен интерпретатор при сборке (решается PyInstaller) | **выбран** |
| C# / WPF | родной Windows, `ProtectedData` из коробки, аккуратный UI | только Windows (macOS/Linux — отдельный проект); нужен .NET SDK и MSIX-подпись; PDF-вёрстка через QuestPDF — доп. лицензионные вопросы | нет |
| Rust / Tauri | малый размер, memory-safe, `keyring`/`ed25519-dalek` | WebView-интерфейс тянет браузерный контейнер; DPAPI — через `windows` crate (объёмный FFI); дольше до рабочего MVP | нет |

Что решило выбор:

1. **Криптография.** `cryptography` (OpenSSL) — эталонная реализация Ed25519;
   никакой самописной математики. В C#/Rust тоже есть хорошие реализации, но
   Python-вариант позволяет держать весь криптокод в одном маленьком и
   читаемом модуле.
2. **PDF.** ReportLab даёт детерминированную A4-вёрстку с реальным текстовым
   слоем и встроенными шрифтами без системных зависимостей (WeasyPrint на
   Windows требует GTK — это вычёркивает связку «HTML-шаблон + WeasyPrint» из
   практичных вариантов).
3. **DPAPI.** Вызывается через `ctypes` (`CryptProtectData`), то есть без
   `pywin32` и без потери кроссплатформенности: на не-Windows этот модуль
   просто не загружается.
4. **GUI.** PySide6 (Qt 6, LGPL) даёт нативный десктопный вид, `QPdfView` для
   честного предпросмотра и нормальные диалоги файлов.

## 2. Слои

```
ui/            PySide6: окно, две вкладки, экран соглашения, предпросмотр PDF
 ├─ app.py, main_window.py, author_panel.py, verify_panel.py, eula_dialog.py
render/        PDF A4, внешний шаблон, шрифты, векторный QR, HTML-фолбэк
├─ pdf.py, template.py, fonts.py, qr.py, preview.py
document.py    «запечатать» / «проверить» — единственный вход в криптологику
├─ identity.py   ключ + подпись
├─ canonical.py  подписываемые байты, строгий разбор
├─ crypto.py     Ed25519, SHA-256, отпечатки
├─ codec.py      VC1.<base64url>, ссылки
├─ storage.py    файлы .poi
├─ eula.py       текст соглашения + факт принятия
└─ keystore/     dpapi.py | keyring_backend.py | ephemeral.py
trust.py       источник доверенного ключа (вшит в сборку)
paths.py       каталог данных и ресурсов
```

Правило зависимостей: `ui → document → (canonical, crypto, codec, identity,
keystore)`; `render` зависит только от `canonical/codec/crypto`. Ни один
низкоуровневый модуль не импортирует `ui` — поэтому криптография тестируется
без графики.

## 3. Потоки

### Запечатывание (режим автора)

```
текст, заголовок
   │ normalize (canonical)
   ▼
ts = now(UTC)                    ← фиксируется сразу, дальше не меняется
   ▼
digest = SHA-256(domain ‖ v ‖ title ‖ text ‖ ts)
   ▼
sig = Ed25519.sign(keystore.sign(digest))   ← ключ живёт только внутри вызова
   ▼
payload → code = VC1.base64url(json)
   ▼
render PDF (A4) → preview → .poi / .pdf / ссылка / QR
```

После нажатия «Запечатать» поля ввода блокируются, форма очищается только
кнопкой «Новый документ».

### Проверка (режим проверки)

```
код (вставка, файл, позже — QR)
   ▼ codec.decode → строгий разбор полей
   ▼ digest = SHA-256(пересчитанных полей)
   ▼ Ed25519.verify(доверенный ключ, digest, sig)
   ▼
valid → PDF из проверенного содержимого + протокол проверки
invalid/malformed → содержимое НЕ показывается
```

## 4. Ключи

### Windows (DPAPI)

```
key.blob = "VC1K" ‖ flags(1 байт) ‖ CryptProtectData(seed)
flags: бит 0x04 = DPAPI локального компьютера (опционально)
```

* `CryptProtectData` вызывается с `CRYPTPROTECT_UI_FORBIDDEN` и
  дополнительной энтропией `b"VaultCore/v1/ed25519-seed"`;
* закрытый сид никогда не пишется открытым текстом и не выводится в UI;
* запись атомарная (временный файл + `os.replace`);
* ошибка расшифровки (чужой ПК/учётка, повреждение) — не молчаливый «новый
  ключ», а явная ошибка с текстом.

`identity.json` хранит **только** открытый ключ, отпечаток, дату создания и имя
механизма. Он не является источником истины: при каждом запуске открытый ключ
пересчитывается из сида, и несовпадение блокирует подпись (защита от подмены
файла метаданных).

### macOS / Linux

`keyring` (Keychain / Secret Service). Уровень защиты ниже, чем у DPAPI: это
зафиксировано в README как ограничение, а не как «эквивалент».

### Нет хранилища

Эфемерный ключ в памяти: приложение работает, но в блоке заверения и в UI
появляется пометка, что подпись нельзя связать с автором после перезапуска.

## 5. Доверие к открытому ключу

| Сборка | Откуда ключ | Можно ли подменить |
|---|---|---|
| Автор | Хранилище ОС | — |
| Проверка | **вшит в `embedded.py`** при сборке | только пересборкой |
| Author dev | не вшит | проверка честно пишет «ключ не задан» |

В интерфейсе нет поля «заменить открытый ключ». Это осознанно: подмена ключа —
действие сборки, а не настройка пользователя.

## 6. PDF

* `BaseDocTemplate` + два `PageTemplate` («первая страница» с полной шапкой,
  «остальные» с компактной);
* двухпроходная сборка: первый проход считает страницы, второй печатает
  «Стр. X из Y»;
* штамп, рамка, шапка и колонтитул рисуются в `onPage` — фоном, чтобы текст
  всегда был поверх штампа;
* QR — **векторный** (`_QRFlowable`): модули рисуются прямоугольниками, код
  печатается резко на любом принтере и не зависит от растра;
* шрифты — TTF, найденные в системе (Times New Roman/Arial на Windows,
  Liberation/DejaVu на Linux, Times/Arial на macOS) и обязательно
  **встроенные** в PDF; стандартный Helvetica ReportLab подменяется нашим TTF,
  чтобы в файле не осталось невстроенных шрифтов;
* оформление — внешний `templates/document.json` (цвета, кегли, поля, тексты),
  путь переопределяется `POI_TEMPLATE`.

## 7. Сборка и упаковка

```
python tools/embed_key.py            # вшить ключ автора в embedded.py
python tools/build_verifier.py       # PyInstaller --onefile --windowed
python tools/make_examples.py        # обновить examples/
```

В сборку «Проверка» попадают только `templates/`, `assets/` и код без
создания авторского ключа; вкладка «Создание» не добавляется (`--mode verify`
по умолчанию).

## 8. Развитие

1. TSA (RFC 3161) — формат v2: поля `tsa`, `tsaCert`; проверка офлайн по
   сохранённому токену.
2. Аппаратный токен (PKCS#11: Рутокен/YubiKey) — заменяет DPAPI для сценария
   «автор недоверенный».
3. Ссылки `https://…/verify` с QR — сейчас формат ссылки есть, публичного
   хоста нет (и сервер не нужен для проверки).
